【钩子】

我在场景里放了第二盏平行光，两个物体并排站着，画面却只认一盏。Console 干净得很，没有报错，没有警告。我把两盏灯轮流关掉又打开，物体亮度纹丝不动。

问题不在灯，在我的 shader 只有一个 Pass，而这个 Pass 的标签写死了只处理主光源。

这集要回答的就是这件事：前向渲染里，多一盏光究竟多了什么。中心命题一句话，前向渲染把每一盏额外的光都当成一次额外的 Pass，光的类型靠变体区分，性能靠逐像素、逐顶点、球谐这三级台阶往下退。听完能拿到四件事：Pass 怎么叠，混合怎么写，衰减怎么采样，变体怎么切。

【用了什么】

先说清楚这两个标签。ForwardBase 是基础通道，负责主方向光，环境光、球谐光和顶点光也在这一趟里算完。ForwardAdd 是附加通道，一盏逐像素光配一个，副方向光、点光源、聚光灯都走这里。

它和延迟渲染的边界要划清。延迟渲染先把几何信息写进 G-buffer，光照统一在屏幕空间算一遍，光的数量和几何复杂度解耦。前向渲染是几何和光照绑在一次绘制里，光越多，Pass 越多，绘制调用越多。这条差别决定了后面所有优化的方向。

还有一层容易混的：光照标签和光源类型是两件事。标签决定这个 Pass 什么时候被调用，光源类型决定 Pass 内部读到的是方向还是坐标。我一开始把这两件事混为一谈，才会在点光源下看到一盏黑灯。

再往外一圈是 cookie。它本质是给光加一张遮罩纹理，方向光的 cookie 无限平铺，聚光灯的是一张圆形的软边遮罩，点光源的是一个立方体贴图。cookie 不改变光的类型，只改变光的分布，所以在变体维度上它是独立的一层。

【为什么用】

旧做法是在每个物体上单独写光照代码。加一盏灯就复制一份 shader，改一次光照模型要翻好几个文件，改漏一个就出现两种风格并存。这种做法在小场景里还撑得住，物体一多就彻底失控。更难受的是调试，同一个 bug 在不同副本里长得不一样，我改完一处就以为修好了，其实另一处还在。

另一个极端是把光全烘焙进光照贴图。静态场景里这确实是最省的路，但一旦物体会动、光会变，烘焙就失效了，而且它完全不给实时反射留余地。室内场景如果光要随剧情切换，就只能走实时这条路。

新办法很朴素：把公共部分搬进一个 cginc，多个 Pass 引用同一份。收益是光照模型只有一处真源，加光只是加 Pass。代价也明确，每个 Pass 都要重新跑一遍顶点和片元，而且这些 Pass 之间没有深度合并，光一多填充率就爆。

另一笔代价是变体。要让同一份代码支持三种光型，就得编译三份指令，再加 cookie 还会继续翻倍。变体数量直接影响编译时间和包体，这一点在项目后期比运行时开销更让人头疼。

什么时候不该用：光数量上到十几个的场景，前向渲染的绘制调用和重复绘制都会失控，这时候应该换成延迟渲染，或者干脆把静态光烘焙进贴图。

回到命题上：Pass 是这套体系的成本单位，加光就是加成本。

【难在哪】

第一个难点，两个 Pass 会互相覆盖。现象是加了附加通道之后，画面只剩副光的效果，主光像被擦掉了。原因是每个 Pass 算完的颜色都会写进帧缓冲，默认混合是源一目标零，也就是直接替换。机制上混合状态属于 Pass 的固定管线配置，我不显式声明，GPU 就按替换处理。这条默认值不写在代码里，写在硬件的状态机里。

第二个难点，同一块像素的深度被写了两次。现象是混上之后出现说不清的闪烁。原因还是那个 Pass 又跑了一遍片元程序，针对的是同一个物体，写进去的深度值和第一次完全一样。机制上深度测试本来是为了让近处像素提前挡住远处的片元，重复写同样的深度没有收益，还会拖慢。所以附加通道里要显式关掉深度写入。

这里值得多看一眼渲染顺序。Unity 对不透明物体是就近优先，先画靠近相机的那一批，被挡住的片元在深度测试这一步就被丢掉，根本进不了片元程序。反过来，如果我从远往近画又不写深度，远处的像素会被后面的覆盖好几遍，这就是重复绘制的来源。我在帧调试器里一步步看过这个过程，附加通道的每一次绘制都落在同一批像素上，开销是一次不落的。

第三个难点，光的方向到底从哪来。方向光被视为无限远，存进光源位置变量里其实是一个朝向；点光源存的是真实坐标。同一行取值代码，在两种光下语义不同。这个问题在只有一盏方向光的时候完全隐形，一加点光源立刻暴露。

三个难点其实同源：我在用同一份代码处理语义不同的光，而 GPU 不知道我的意图，它只认状态和标签。

【从0到1】

里程碑一，把公共代码抽出去。

目标是让多个 Pass 共享一份光照实现。输入是原来的单光 shader，输出是一个 cginc 加一个变薄的 shader 外壳。做法是把 pragma 以下到结束标记以上的内容整体搬进 cginc，外面套一层头文件保护，如果没有定义过这个标记就定义它，然后放正文。这层保护的语义是防止同一个文件被重复展开，因为后面会有多个 Pass 各 include 一次。

验证方法很直接，编译通过，画面和抽离之前逐像素一致。这一步不改行为，只改结构，所以任何视觉差异都说明搬错了。

里程碑二，加第二个 Pass 并让它叠加。

目标是让副光真正参与计算，而且结果是相加而不是覆盖。做法是在 SubShader 里再写一个 Pass，光照标签从基础改成附加，前缀指令和 include 与第一个完全一样；然后在附加通道里加一行混合，源因子和目标因子都设为一，再加一行关闭深度写入。

物理意义是：新算出来的颜色整份加到已有颜色上，不做透明度加权。为什么是相加而不是平均，因为光照在物理上是叠加的，两盏灯照同一块表面，接收到的能量就是两份。

验证方法分两步。先一次只激活一盏灯，两次截图的亮度应该分别对应各自的灯。如果第二次纯黑，说明标签没被识别，Unity 根本没把附加通道派给副光。再两盏同开，整体亮度应当是单盏的两倍左右，这才说明混合写对了。如果亮度和单盏一样，多半是混合又被覆盖回去了。

里程碑三，让同一份代码支持不同光型。

目标是消掉对方向光的假设。做法是在附加通道用 multi_compile 声明两个关键字，一个表示方向光，一个表示点光源，然后在算光方向的函数里用条件编译分成两支：点光源用光源坐标减去片元世界坐标再归一化，方向光直接用那一行朝向。取值的判断只做一次，后面的着色模型完全不关心光是什么类型。

验证方法是打开编译后的变体文件，应该能看到两个变体，运行中切换光源类型时 Unity 会自己挑变体。如果没有变体生成，多半是声明写在了错误的 Pass 里，或者关键字拼写和条件编译那一边不一致。

这一步顺手解决了衰减。点光源有明确位置，亮度随距离的平方反比下降。这个规律的物理来源很直观：光子从一个点向四面八方扩散，某一时刻它们分布在一个球面上，球的表面积是四倍圆周率乘半径平方，光子密度就是这个面积分之一。所以衰减因子是距离平方的倒数。

但直接用平方倒数有个问题，距离趋近零时亮度会趋近无穷大，靠近光源的地方会出现一片惨白。所以实际用的是加一之后的倒数，让最近处的值收敛到一。

手写这个公式只能做到大致对，它和光源范围对不上。我把衰减交给 Unity 的宏，它内部先把片元世界坐标乘以世界到光源的矩阵，转进光源空间，再用距离的平方去采样一张衰减纹理。光源空间里点光源在原点，范围外的点距离平方就超过一，采样结果自然趋近零，这样衰减和范围就同步了。

那个宏有三个参数：接收结果的变量名、用于阴影衰减的输入、片元世界坐标。它在内部把世界坐标转成一个光源空间坐标，再拿这个坐标和它自己点乘，把结果当成一维纹理坐标去采样。纹理本来是一维的，所以取一个分量重复两次凑成二维坐标就够了，第二个分量没有意义。通道的选择还取决于目标平台，有的平台读红色通道，有的读透明通道。

这一步的验证方法是把范围从十缩到一，物体进出范围时亮度不应该跳变。如果跳了，说明我还在用手写衰减。

里程碑四，把多余的光降到顶点。

目标是解决像素光上限带来的矛盾。基础通道只认主方向光，其余逐像素光按强度和距离排序，超出数量的会被丢掉，物体一移动亮度就跳。

做法是在基础通道加一个顶点光关键字，在插值结构体里多传一个顶点光颜色，在顶点函数里把光的位置从三个分量数组里按索引取出来，算方向和衰减，得到颜色。顶点光的坐标不是直接存成向量，而是拆成横、纵、竖三个四分量数组，第几盏光就取第几个分量，这样四盏光能压进十二个浮点数里。

然后把顶点光颜色当作间接光的漫反射，加进最后的着色结果。这个处理方式很像环境光，因为顶点光本来就是低频的。

验证方法把像素光数量调成零，物体应该是带对应光色的剪影，而不是纯黑。如果还是纯黑，说明顶点光那一支没有被编译进去。

如果要支持四盏顶点光，逐个手写太啰嗦，Unity 提供了一个现成函数，参数是三个光位置分量、四个光色、四个衰减和顶点世界坐标、法线。它的实现里有个细节值得记：算完点积之后乘的是平方根的倒数，避免开方再除法，一处小优化乘四盏光就是四份收益。验证方法是同时放四盏顶点光，四个方向都应该有对应的亮面。

这里有条边界必须记住：Unity 自带的这套顶点光只支持点光源，方向光和聚光灯不会被塞进来。它和那种我自己在顶点函数里算法线、算半角向量、算完整着色模型的做法也不是一回事，后者我完全可以做，代价是精度只到顶点级别。管线的顶点光只算漫反射，目的是用很便宜的方式补一点光照，不是替代逐像素光照。

里程碑五，把剩下的光压成球谐。

目标是让四面八方的弱光也能参与，而不是被丢掉。球谐的思想是用一组低频函数近似描述入射光在球面上的分布，拿到法线就能采样出颜色。它只保留低频，所以只能表达缓慢变化的照明，方向光那种明确的高光它给不出来。

Unity 预先把环境光烘成七组四分量系数，采样函数分两步：先做常数项和一次项的线性组合，再做四个二次项和第五个二次项，最后相加。实现里还有一处颜色空间判断，伽马空间下要做一次线性到伽马的转换。

如果把这九项拆开写，最后会化成一个多项式：一个常数，一个正比于法线纵分量的项，一个正比于横分量的项，一个正比于竖分量的项，然后是两个分量的乘积项，一个分量的平方项，最后是横平方减纵平方这一项。九项的系数都由那七组预烘数据给出。听的时候不需要记住每一项，只要知道它是一组固定系数的二次多项式就够了。

做法是在间接光里加一项，用片元法线采样球谐，再和顶点光、漫反射间接光相加。注意取零截断，因为球谐重建出来可能是负值，负的光照没有物理意义。

这里有个容易踩的坑：它不能和顶点光共用同一个关键字，要单独定义一个只在基础通道生效的关键字。原因是顶点光和球谐光的启用条件不同，混用一个会让两个 Pass 都算进去。验证方法是关掉所有灯只留天空盒，物体应该有隐约的环境色，而不是死黑。

五步走完，多光源这条链就闭合了。再加光，就是在附加通道再跑一遍。

【踩坑与边界】

第一坑，动态批处理失效。现象是灯一多，绘制批次不是按物体数简单翻倍，因为阴影通道和动态批处理都会插进来。根因是 Unity 规定动态批处理只支持受一盏方向光影响的物体，第二盏光进来这条规则就作废了。修复方法是别指望多光场景靠它省绘制，改用静态合批或者干脆接受这个数字。

第二坑，场景里有光但画面不动。症状是无论如何调光，物体亮度不变。根因是衰减宏要求在使用前定义光型宏，而这个定义必须在引用自动光照文件之前生效，顺序错了宏就走另一条分支。修复方法是把定义挪到 include 前面。

第三坑，聚光灯衰减多了一道遮罩。现象是聚光灯照出来是一团边缘模糊的圆。根因是它的衰减不只算距离，还要把光源空间里的横纵坐标当纹理坐标，去采样一张圆形遮罩；同时还有一步把原点后面的点强制衰减为零，把光限制在锥体前面。机制上光空间转换是一次透视变换，所以要用齐次坐标除完再取样。

第四坑，球谐在伽马空间偏亮。现象是只留天空盒时物体白得刺眼。根因是程序化天空盒代表一个理想晴天，白色表面会接收大量环境光，伽马空间把这个差距放大。真实世界里几乎没有完全白色的表面。修复方法不是改代码，是接受这个物理事实，或者把环境强度调低。

第五坑，cookie 让变体翻倍。方向光的 cookie 是无限平铺的，边缘必须无缝；点光源的 cookie 是一个立方体贴图，还要额外指定映射模式。每多一种带 cookie 的光型，附加通道就多一个变体。如果把关键字的排列组合全编进去，编译时间会明显变长。修复方法是按目标平台裁剪变体。

边界也要说清。点光源和聚光灯都有范围，范围越小，参与绘制的物体越少，帧率越高，这是最便宜的一档优化。顶点光不管物体在不在范围内，计算量都是固定的四盏。球谐只保留低频，快速变化的照明它表达不出来。

【收束】

三句话收个尾。前向渲染里，多一盏逐像素光就是多一个 Pass，混合和深度写入必须手动配对。光型差异靠变体解决，不靠分支去猜。性能不够时，按逐像素、逐顶点、球谐的顺序往下退。

什么时候该用：光少、物体多、移动端，前向渲染加上顶点光和球谐的组合最划算。什么时候不该用：光多、材质复杂、需要大量局部光照，直接上延迟渲染。
