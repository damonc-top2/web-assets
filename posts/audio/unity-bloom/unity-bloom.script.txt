【钩子】

场景很简单：黑色背景，一堆纯白的球和立方体，摄像机开了 HDR。我想让最亮的那几块往外渗一点光，像摄影里镜头吃光那样。第一反应是拿模糊滤镜糊一遍，结果整张图都变糊了，暗部也被拖脏。第二反应是只糊亮的像素，可大核模糊要采样几百次，分辨率一高就跑不动。

这一集做的效果叫 Bloom，我把它拆成三步：先按亮度挑出该发光的像素，再逐级缩小做成一张模糊图，最后逐级放大并加回原图。中心命题是：Bloom 的难点不在模糊公式，而在一串临时纹理的生命周期，以及最后一次合成不能糊在还没内容的画布上。

【用了什么】

先把光的范围说清楚。显示器能出的光有上限，Shader 里对应 RGB 从 0 到 1，这叫低动态范围，也就是 LDR。现实里的光没有上限，为了表示特别亮的颜色，可以不强行截到 1，这就进入高动态范围，HDR。前提是输入和输出的纹理格式都能存大于 1 的值。

但显示器还是出不了那么亮，所以最后必须把 HDR 压回 LDR，这个过程叫色调映射 tonemapping，做法是非线性地把图变暗，让原本挤在一起的高亮区分开来。它和自动曝光可以一起用。不过眼睛并不是总能适应，有些场景实在太亮，怎么压都看不清，Bloom 就是用来在受限的显示器上表达这种过亮的手段。Bloom 是这条链路上的一个环节，通常的顺序是先自动曝光，再 Bloom，最后色调映射。这一集只做 Bloom，其余都不加，所以超出显示范围的颜色最后会被直接截断。

Bloom 本身的定义很朴素：让像素的颜色渗进相邻像素，而且渗的强度跟亮度相关。它有点像光在眼睛里扩散，但更多是一种非现实的效果。文章里专门提醒了一句，很多人讨厌 Bloom，因为它把清晰的画面弄脏，让东西不真实地发光。问题不在 Bloom，在滥用。追求真实感就克制地用，追求风格化可以放开用。

它和相邻后处理技术的边界：雾是往远处混颜色，景深是按深度混模糊，Bloom 只关心亮度。三者都是往临时纹理里搬图，工程套路一样，效果逻辑完全不同。

【为什么用】

旧办法有两个，都不好用。

第一个是直接上大核模糊。滤波核 filter kernel 指的是每个像素要组合周围哪些像素。核越大越糊，采样次数也越多，而且是每个像素都采一遍。核再大一点，全屏跑一遍的成本就很难看。

第二个是缩小分辨率再糊。这看起来是偷懒，其实是正解，因为 GPU 的双线性过滤 bilinear filtering 自带平均。把纹理缩到一半，每四个源像素正好合成一个，采样点落在四个像素中间，结果就是它们的平均值，一次采样都不用额外写。这就是降采样 downsampling 的全部秘密。

收益是成本断崖式下降。半分辨率意味着四分之一的像素，四分之一的工作量，而且模糊半径在视觉上反而更大。代价是结果偏块：这一步每个像素实际上只混合了周围 4×4 的区域，而且对齐方式只有四种，所以画面会明显发块。想糊得更开，就得继续往下减半，但块状也会更明显，因为信息已经被丢掉了。

代价有三个。第一，直接砍到低分辨率会丢像素，只保留孤立的四像素组的平均值，画面会块状。第二，必须用 HDR 的纹理格式，否则亮部信息在第一步就被截断，Bloom 无从谈起。第三，会多出一串临时纹理，管理不好就是性能灾难或者画面脏。

什么时候不该用。画面整体偏暗、或者亮部本来就不多的时候，Bloom 基本看不出来，纯属浪费。需要精确色彩还原的场合也不适合。

所以整件事的重点，从「怎么模糊」变成了「怎么管这串纹理」。这就是中心命题。

【难在哪】

三个难点。

第一个难点，临时纹理的生命周期。现象是，明明显存够用，申请到的纹理却总像是新建的，池子等于白建。原因是渲染纹理由引擎池化管理，申请和归还必须严格配对，忘了归还，同一块内存就一直被占着，下一轮拿不到可复用的缓存。机制上要用引擎提供的临时纹理池：申请的时候给尺寸、深度和格式，用完必须归还。归还这一步最容易被忘，因为它不影响画面，只影响性能。

第二个难点，尺寸会缩到零。现象是，把迭代次数拉大，画面直接消失或者报错。原因是每一步尺寸减半，整数除法在很小的尺寸上会变成 0，之后的纹理申请就没有意义了。机制上的解法是在减半之后立刻检查，低于一个阈值就跳出循环。文章里用高度来判断，因为显示器通常是横的。要支持竖屏就同时看宽高。

第三个难点，叠加到还没有内容的画布上。现象是，最后一步用叠加混合，画面整体过曝，甚至每帧越积越亮。原因是中间那些升采样步骤是把新一层加到上一层上，那一层本来就有内容；但最终目标是摄像机给的一张空纹理，往空纹理上叠加，等于加到一个未定义的值上。机制上的解法是给最后一次合成单独写一个 Pass，在里面显式地把原图和模糊图相加，而不是依赖混合模式。

【从0到1】

五个里程碑。

第一个里程碑，效果组件和临时纹理。目标是让摄像机多一个后处理组件，管线从直拷变成两段。做法是新建一个继承自 MonoBehaviour 的组件，加上编辑模式执行和允许在场景视图生效两个属性，然后实现渲染图像回调。回调一进来先申请一张和源同尺寸的临时纹理：申请函数负责创建、缓存、销毁，只需要给尺寸；第三个参数用 0 表示不要深度缓冲，因为后面只做颜色运算；第四个参数直接用源纹理的格式，摄像机开了 HDR 之后源格式就是对的，通常是半精度四通道。然后先拷到临时纹理，再从临时纹理拷到目标，最后归还。

验证方法是画面不变，但管线已经从中间走了一遍。这一步的收益是后面所有模糊都在这张临时纹理上做，摄像机给的源和目标都不用碰。

接着做第一次真正的模糊：把临时纹理的宽高各减半。因为双线性过滤会自动平均，这一步等价于每个像素和周围 4×4 的区域混合。然后再拷回原尺寸，这就是一次升采样 upsample。验证方法是画面变块、轻微变糊，但亮部确实扩散了一点。

第二个里程碑，改成一串逐级减半。目标是避免一次性砍到低分辨率造成的丢像素。做法是把变量从单个临时纹理改成当前目标，第一段之后把当前目标记成当前源；然后用一个循环，从第二次开始，每轮先把宽高减半、申请新纹理、把当前源拷进去、归还当前源、再把新纹理变成当前源。循环次数由一个 1 到 16 的滑动条控制，16 次足够把六万多像素的边长一路缩到一个像素。

循环里必须加那道保护：减半之后如果高度小于 2 就跳出，否则尺寸会归零，之后的申请就没有意义。文章里用高度判断是因为显示器通常是横的，要支持竖屏就同时看宽高。

然后是逐级升采样。这里遇到一个资源管理上的小坑：如果每级都先归还再重新申请，同一个尺寸会被申请两次。做法是开一个固定 16 个槽的数组，每次申请到临时纹理就顺手存进去。

于是写两个循环。第一个只降采样，注意它不再归还当前源，因为后面还要用；第二个从最低层往回走，起点是第一个循环的迭代器减 2，一路减到 0。每一轮把数组里对应槽位的纹理取出来当目标，把槽位置空，从当前源拷过去，再归还当前源，然后把目标变成新的源。

验证方法是把迭代次数从 1 拉到 16，画面应该越来越糊，但不会黑屏，也不会越升越亮。如果黑屏，多半是保护判断写在了申请之后；如果亮度不对，多半是某一步归还和赋值的顺序反了。

第三个里程碑，自定义 Shader 和盒式采样。目标是让模糊质量再上一层，并且给降采样和升采样不同的核。

先建一个极简的 Shader：一个主纹理属性，关闭剔除，深度测试始终通过，不写深度；顶点和片元共用的部分放进公共代码块，只负责把位置转到裁剪空间、把 UV 传下去。片元先只做一件事，采样主纹理并乘上红色，用来确认用的确实是这个 Shader。采样用半精度类型，因为 HDR 颜色通常就是半精度存储的，在移动平台之外其实差别不大。

然后加一个纹素尺寸变量，注意它对应的是源纹理的纹素 texel，不是目标的。写一个采样函数返回颜色的 RGB 三通道，再写盒式采样：用纹素尺寸构造四个对角方向的偏移，采四次，求和除以四。四个样本分别落在四个相邻的 2×2 块里，合起来正好覆盖 4×4 的区域，等于把核的边长又翻了一倍。

关键的一步是把偏移量变成参数。降采样用 1，升采样用 0.5。0.5 的时候四个样本互相重叠，覆盖的是 3×3 的区域。按原文的描述，中间像素参与所有样本，对角像素只用一次，其他像素出现两次，权重分布更集中，边缘也更干净。

两个 Pass 就这么分出来。为了方便，把 Pass 索引定义成常量，别用裸数字。

验证方法：先只看降采样结果，应该比纯双线性更平滑；再打开升采样，应该没有明显的方块感。如果升采样比降采样还糊，多半是偏移量没换。

第四个里程碑，叠加混合和独立合成。目标是让模糊图只加亮部，而不是盖住整张图。

第一步是叠加混合。三通道各自相加，相当于把新一层加到上一层上，而不是替换它。给升采样的 Pass 设成源和目标都乘 1 的叠加模式，中间每一层都成立。

但最后一次不对。最终目标是摄像机给的一张空纹理，往空纹理上叠加，等于加到一个未定义的值上，可能整体过曝，也可能看 Unity 怎么复用纹理而随机变化。机制上的解法是再复制一个 Pass，用它显式地采样原图，再把盒式采样的结果加上去，混合模式回到默认。为了让这个 Pass 拿得到原图，还要给 Shader 多一个源纹理变量，在拷贝之前把它设进材质。

验证方法是把时间轴暂停，反复看同一帧，画面应该完全稳定。

第五个里程碑，阈值、软拐点和强度。目标是让 Bloom 只吃超过显示范围的亮度。

加一个 0 到 10 的滑动条，默认 1，正好把 LDR 的像素排除掉。给 Shader 加一个阈值变量，写一个预过滤函数。先取 RGB 三个通道里最大的那个当亮度，因为任何一个通道足够亮，这个像素就够亮。再用亮度减阈值，得到超出量。物理意义很直白：超出量越大，参与发光越多；刚好等于阈值时完全不参与。把超出量除以亮度，得到零到一的贡献系数，除数加一个极小值防止除零。阈值设 0 时系数恒为 1，颜色不变；阈值越大，亮度曲线往下弯，在亮度等于阈值处降到零。这条曲线的拐点形状让它得名拐点 knee。

阈值必须作用在模糊链的最前面，因为后面每一步都在混合，晚加就收不回来了。所以要再复制一个 Pass 放在最前面，把所有后续 Pass 的索引整体加一。

然后是软阈值。硬拐点在零处有一个折角，所以在发光和不发光之间是硬切，大球上能看到一条清晰的边界。软阈值就是用一条二次曲线把折角磨圆：在亮度和阈值之间预留一个带宽，带宽等于阈值乘软阈值系数；把差值抬高一个带宽，截断在零到两倍带宽之间，再平方、除以四倍带宽。这条曲线在零处斜率为零，所以能从零平滑地接上。

最后取软曲线和原来那条直线里较大的那个。系数设 0 就是硬拐点，设 1 时从零亮度就开始平滑淡入，默认取 0.5。

这里还能省一点算力。软拐点公式里有一部分只依赖配置，每个 Pass 都是常数，可以预先在 C Sharp 脚本里算好，打包成一个四分量向量传给 Shader：第一个是阈值，第二个是阈值减带宽，第三个是两倍带宽，第四个是四倍带宽的倒数。Shader 里就只剩几次乘加。

最后是强度。加一个 0 到 10 的滑动条，默认 1，把值乘在最后两个 Pass 的采样结果上。因为业界习惯用伽马空间里的数值调 Bloom 强度，所以传进 Shader 之前要做一次伽马到线性的转换。验证方法是拉到 0 应该完全没有光晕，拉到 10 应该过曝到看不清结构。

到这一步，中心命题的两个关键点都验过了：临时纹理严格配对归还，最后一次合成单独走一个 Pass。

【踩坑与边界】

五个坑。

第一个坑，尺寸归零。症状是迭代次数一高就黑屏。根因是整数除法把宽高算成 0。修复是在减半之后、申请纹理之前判断，低于阈值就跳出。

第二个坑，临时纹理泄漏。症状是帧率随时间下降。根因是某个分支忘了归还，或者数组槽位没有置空。修复是让申请和归还严格配对，数组槽位用完立刻置空，循环里出现异常路径时也要还。

第三个坑，最终目标没有初始内容。症状是叠加后整体过亮，或者亮度随机变化。根因是往一张未定义的纹理上做叠加。修复是最后一步用独立 Pass 显式相加，不依赖混合状态。

第四个坑，阈值设了却看不到效果。症状是滑动条拉到 1 以上画面没变化。根因是场景里没有真正的 HDR 像素。修复是给材质加自发光或者加强光照。文章里提到一个容易误判的现象：默认 Unity 场景很亮，环境光和反射叠加之后，某些白色表面本身就能超过 1，这些白像素也会被算进 Bloom。

第五个坑，格式选错。症状是亮部细节丢失、光晕发灰。根因是用 8 位格式存 HDR，大于 1 的部分在第一步就被截断。修复是直接沿用源纹理的格式，不要自己指定。

边界和性能。迭代次数越多，申请和拷贝的临时纹理就越多，成本随分辨率和迭代次数上升。移动平台要注意半精度类型的支持情况。这套实现和 Unity 的 Post Processing Stack v2 的 Bloom 非常接近，但简化了很多，比如没有做色调、采样偏移不可配、滤波器只有盒式。

【收束】

三句话。Bloom 是把超过显示范围的亮度挑出来，做成一张逐级模糊的图，再加回原图。模糊靠降采样免费完成，质量靠盒式采样和软拐点找回来。真正难的是临时纹理的配对归还，以及最后一次合成必须显式相加。

什么时候该用：画面有明确高光源、想引导注意力或者做风格化的时候用它；追求色彩准确、或者场景本来就暗的时候别用。

下一集继续做后处理，但换个维度。要根据深度缓冲算出每个像素的失焦程度，再按这个程度混一张散景图，也就是景深。
