【钩子】
我把项目的渲染路径从一个下拉框切到 Deferred，然后盯着 Frame Debugger 数 Draw Call。场景是 64 个可见物体组成的同一个预制体，两盏平行光。前向渲染不开阴影是 132 次，延迟渲染不开阴影只有 52 次。前向开阴影涨到 408 次，延迟开阴影是 231 次。
差距不是靠优化指令换来的，是靠换一个计算顺序换来的。这一集我只回答一句话，延迟渲染把几何计算只做一遍存进屏幕缓冲区，再按像素算光，所以光越多它越划算，代价是带宽和抗锯齿。
听完能拿到的是三样东西。一是 G-Buffer 四张贴图分别装了什么。二是为什么延迟 pass 里要故意把光照算成零。三是 LDR 路径下颜色会被 exp2 编码，自发光和环境光都得跟着编。

【用了什么】
延迟渲染的关键词是 G-Buffer，直译几何缓冲。它是 MRT，多渲染目标的产物，一次绘制同时写好几张贴图。Unity 的延迟路径用四张。
RT0 装 albedo 和 occlusion，RT1 装高光色调和 smoothness，RT2 装世界空间法线，RT3 装 emission 和反射。
它和 forward 的边界必须说清楚。前向渲染在 base pass 里把光照算完，像素直接出颜色。延迟渲染的 base 阶段只填数据，不碰光。光照被推迟到几何全部填完之后，单独一遍。
光在这个阶段也要被渲染。平行光是一个铺满屏幕的面片，走内置的 Internal-DeferredShading 着色器。聚光灯是一个金字塔形网格，点光源是球体，都先写模板缓冲，再只对体积内的像素算光。
它替代不了后处理。抗锯齿得另找办法，这是它的结构性限制，后面会讲。

【为什么用】
旧办法的痛点在 additive pass 上。前向渲染里，每多一盏光，每个被照到的物体就要再跑一遍完整流程。取网格数据，转到正确空间，插值传参，采样材质属性，算光照。
additive 比 base 便宜一点，因为深度缓冲已经准备好了，它也不用关心间接光。但几何那部分工作在重复。
延迟的想法很朴素。这些几何量每个像素只跟物体本身有关，跟有几盏光无关。那就存一次。
收益立刻显现。光数量和物体数量解耦了。原文的说法是，每多一盏不投影的光，只增加一点工作。Pixel Light Count 这个设置也随之失效，因为所有光对范围内的物体都是逐像素着色。
代价在带宽。四张 G-Buffer 合并后，每个像素 LDR 是 160 位，HDR 是 192 位。普通颜色缓冲才 32 位，差了好几倍。移动 GPU 对位宽敏感，桌面则没问题。
不该用的场合也很清楚。移动端带宽吃紧，或者需要 MSAA。这两种情况下前向更稳。
回到中心命题，省下来的不是指令，是重复的几何处理。

【难在哪】
第一个难点，一个像素的所有数据要拆进四张格式固定的贴图。
现象是法线装进去了，但 alpha 通道只剩两位，几乎存不了东西。
原因是 RT2 用的是 ARGB2101010 格式，RGB 每个通道 10 位，alpha 只有 2 位。10 位比常见的 8 位多两位，存法线反而更精确。
机制是这样的。法线分量在负一到一之间，贴图只能存零到一，所以编码时乘 0.5 加 0.5，解码时反过来。多出来的两位正好补上这次重映射的损耗，代价是 alpha 被压到 2 位，只能当作占位。
第二个难点，光照阶段拿不到材质语义。
现象是延迟 pass 里算出的颜色明显偏亮，阴影像是叠了两遍。
原因是 G-Buffer 只存几何和材质参数，光根本不在里面。
机制是，延迟 pass 里光源必须退化成空壳。方向给一个常量，颜色清成零，ndotl 那一步不再相乘。真正算光的是内置着色器，每个像素去读 G-Buffer。原文代码里那行 ndotl 是被划掉的，就是这个意思。
第三个难点，LDR 的动态范围。
现象是关掉 HDR 后，延迟的结果比前向偏色，自发光和环境光尤其明显。
原因是 LDR 缓冲只有 10 位整数，存不下高动态范围的颜色。
机制是 Unity 用 exp2 做对数编码，把大范围压进可表示区间，后处理阶段再解码回主纹理。凡是参与编码的量，自发光和环境光都算在内。
这三个难点都指向同一件事。延迟把数据和控制流拆开了，拆开之后每个阶段的约定必须手动守住。

【从0到1】
第一个里程碑，加一个延迟 pass。
目标是让这个 shader 参与 G-Buffer 填充。
关键语义只有两点。Pass 的光照标签设成 Deferred，pass 写在哪个位置无所谓。编译目标定在 3.0，并且把不支持 MRT 的渲染器排除掉，否则在那类设备上这个 pass 会出问题。
验证方法，打开 Frame Debugger，能看到这个物体进入了 G-Buffer 那一批绘制。
第二个里程碑，改片元返回结构。
目标是一次输出四张。
关键语义，结构体里用四个目标语义，从第零张排到第三张，外面用编译宏切成两套。延迟走四输出，前向还是单输出。结构体要先初始化清零，不加这句编译器会告警。
验证方法，四张 RT 在 Scene 视图的 Deferred 选项下都有内容，不是全黑也不是全白。
第三个里程碑，填前两张。
RT0 的 RGB 放 albedo，alpha 放 occlusion。RT1 的 RGB 放高光色调，alpha 放 smoothness。
这两张都是 ARGB32 格式，各通道八位，够用。
验证方法，把 Scene 视图切到 Deferred 的单张显示，RT0 看起来应该像去掉光照的固有色贴图，RT1 在没有高光的物体上接近黑。
第四个里程碑，填后两张。
RT2 存世界空间法线，编码就是乘 0.5 加 0.5，alpha 给 1。RT3 直接写当前颜色，它承载的是自发光和反射。
RT3 的格式跟 HDR 开关走，LDR 下是 ARGB2101010，HDR 下是 ARGBHalf，每个通道 16 位浮点，总共 64 位，内存翻倍。
验证方法，RT2 看起来是一张偏紫的彩色图，RT3 在没有自发光时接近黑，有自发光时那块区域亮起来。
第五个里程碑，把光照从延迟 pass 里摘掉。
目标是避免重复计算。
关键语义有两处。延迟分支下，光源方向给个占位值，颜色清零，ndotl 不再相乘。取自发光的函数要把延迟分支也包含进去，否则自发光在延迟路径里整个丢失。
验证方法，做一个只有自发光的物体，切换渲染路径，亮度应该一致。
第六个里程碑，处理 HDR 与 LDR。
目标是让 LDR 路径下颜色对得上。
关键语义，用一个多编译开关区分两种模式。没有开 HDR 时，对颜色取负再做以 2 为底的指数。自发光和环境光用同样方式编码。原文里还有一句提醒，开启 HDR 时延迟和前向效果几乎一致，关掉 HDR 时延迟如果不做这段编码就是错的。
验证方法，同一个场景来回切 HDR 开关，关掉时前后向的观感应该接近，而不是一个发灰一个发亮。

【踩坑与边界】
第一个坑，打开 MSAA，相机直接报警。
根因是延迟依赖每像素存一份数据，而 MSAA 靠子像素采样。两者在原理上冲突。原文说得很直白，三角形边缘还是能从 MSAA 受益，但延迟的数据依旧会混叠。
修复方式是关掉，改用后处理抗锯齿。
第二个坑，聚光灯的体积和相机近平面相交，光漏到不该亮的地方。
根因是模板测试按体积裁剪，体积被近平面切掉之后就不是封闭体了。
修复方式是拉开灯和相机的距离，或者这类灯干脆不要走延迟。
第三个坑，反射不按物体混合，而是按像素混合。
根因是反射探针也走模板体积那一套，用探针盒大小的网格写模板缓冲，再屏蔽盒外的像素。
后果是不能再用锚点重写去强制某个物体使用指定的反射探针。原文说，有时候这是保证反射正确的唯一手段。
修复方式，关掉内置的延迟反射，在延迟 pass 里自己采样。还要注意采样黑色探针是纯浪费，所以要用 UNITY_ENABLE_REFLECTION_BUFFERS 这个宏判断当前是否真的需要采样。
第四个坑，混合使用两种路径。
现象是前向物体在 G-Buffer 阶段不可见，后面才补上。
根因是前向物体要单独渲染一遍深度，输出黑色轮廓覆盖之前的片元。
这不是 bug，是顺序决定的，但排查画面缺失时很容易误判。
边界方面，移动端带宽吃紧，160 位和 192 位这两个数字就是门槛。桌面端不存在这个问题。

【收束】
三句话。延迟渲染把几何计算存进 G-Buffer，让光照按像素而不是按物体走。它的收益随光数量放大，代价是带宽和抗锯齿。四张缓冲的格式和 HDR 与 LDR 的编码，是它几乎所有坑的来源。
什么时候该用，多盏实时光的桌面场景。什么时候不该用，移动端带宽吃紧，或者需要 MSAA。
