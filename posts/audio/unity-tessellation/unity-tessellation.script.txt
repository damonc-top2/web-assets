【钩子】

之前做平面线框着色的时候，画面里每个三角形都清清楚楚。可摄像机一拉近，边缘的锯齿和平面感就露出来了，网格像一张折纸。想让表面变细，最直接的办法是回建模软件里把模型细分得更多，代价是网格变大，存储、内存带宽跟着一起涨。这一集我换了一条路：让 GPU 在真正需要的时候自己切三角形，这就是曲面细分，tessellation。

中心命题只有一句：曲面细分不是往着色器里多塞一个程序，而是把顶点阶段拆成控制点、Hull、Domain 三段接力，任何一段的语义没对齐，整条管线都跑不起来。

听完这一集，能搞清楚三件事：三角形到底是怎么被切开的，因子怎么控制切口密度，以及一个只在 OpenGL Core 上冒出来的内部因子 bug。

【用了什么】

先给定义。曲面细分是把一个三角形 Patch 切成一堆覆盖同一片空间的小三角形。要区分一下，GPU 本身也会细分三角形，比如三角形被裁剪的时候，但那是硬件自己做的，控制不了。这里说的是管线里一个可配置的阶段，位置在顶点着色器和片元着色器之间。

它不是单个程序。要让它工作，需要 Hull 程序和 Domain 程序两个入口，再加一个 Patch Constant 函数。Hull 程序负责把 Patch 里的控制点逐个送进细分阶段，Patch Constant 函数提供决定切法的四个因子，Domain 程序根据切分结果生成最终顶点。中间还有一个真正的细分器，它只做几何切割，不生成任何顶点数据。顺带记一个叫法：Domain 程序在 HLSL 里也叫几何评估着色器，说的是同一个东西。

这个阶段的能力范围比想象中宽。它和几何着色器一样灵活，能处理三角形、四边形，也能处理等值线，具体处理哪种由声明告诉它。这一集只做三角形，因为网格本来就是三角形拼的。

和相邻技术的边界也要说清楚。几何着色器 geometry shader 能做的是增删顶点、改图元类型，它和曲面细分不冲突，可以串起来用。曲面细分解决的是密度问题，几何着色器解决的是造型问题。这一集只碰密度。

还有一个必须提前记住的约束：用曲面细分的 Shader Target 最低是 4.6。不手动写，Unity 会警告然后自动升到 4.6。

【为什么用】

旧办法是加面。想要细节就回建模软件再细分一次，导出更大的模型。痛点是三个：模型体积、内存占用、内存带宽，三样一起涨，而且是场景里所有实例一起涨，哪怕远处只占屏幕上几个像素。

曲面细分的收益是按需付费。近处多切，远处少切，同一份网格能在不同距离呈现不同密度。顶点数不再是美术资产里的常数，而是运行时算出来的。

代价也很实在。第一，GPU 要多干活，细分器本身有成本，切出来的顶点还要跑一遍 Domain。第二，它不是免费的开关，Hull 程序那五个属性写错就直接报错，调试门槛比普通着色器高。第三，和 GPU Instancing 不能同时用。文章里写得很明确，Unity 目前不支持这两个一起开，所以我把 multi-compile 指令整段注释掉，Shader 面板里的 Instancing 选项也一起消失。

什么时候不该用。如果模型本来就够密，或者细节能用法线贴图糊弄过去，就别开。曲面细分是给轮廓和剪影用的，法线贴图是给表面纹理用的，两者的成本差一个量级。真要近处精细、远处粗糙，更省事的做法是 LOD Group：零级用带曲面细分的非实例化材质，其余级别用实例化的普通材质。这也顺带绕开了和 Instancing 的冲突。

回到中心命题：三段接力，缺一段就跑不起来。

【难在哪】

有三个难点，全卡在语义上。

第一个难点，Hull 阶段的输入不是顶点，是 Patch。现象是，按习惯写一个接受单顶点的 Hull 函数，编译器不认。原因是 Hull 程序操作的对象叫 Surface Patch，它是网格顶点的集合。机制上要显式声明三件事：用 InputPatch 包住数据结构，用第二个模板参数写明一个 Patch 里几个顶点，三角形就是三个。这和几何着色器声明流参数是同一个套路。

这里还有个容易忽略的细节。Patch 只是集合，里面装什么结构必须自己指定。文章一开始直接沿用了顶点阶段的数据结构，连参数格式都没换。它在逻辑上并不严谨，因为 Hull 在顶点阶段之后，输入类型理应和顶点函数的输出类型一致，只是这一步先绕过去了，后面第五个里程碑才补上这个洞。

第二个难点，Hull 程序一次只输出一个顶点。现象是，明明拿到了整个 Patch，函数签名却要求返回单个顶点，还要多一个参数。原因是 GPU 会对 Patch 里的每个控制点调用一次 Hull 函数，那个额外参数带 SV_OutputControlPointID 语义，是个无符号整数，告诉本次调用该处理哪个控制点。机制上函数体只有一句，用这个编号索引 Patch 再返回。所以「整个 Patch 进、一个控制点出」是它的常态，不是特例。

第三个难点，真正决定怎么切的是 Patch Constant 函数，而它的返回值是一组因子。现象是，Hull 程序写完了，三角形却纹丝不动。原因是细分密度不由 Hull 程序决定，而由一个独立子阶段决定，这个子阶段和 Hull 程序并行跑，每个 Patch 只调用一次，所以叫 Constant，在整个 Patch 上保持不变。机制上它返回四个因子：三条边各一个，三角形内部一个。三个边因子用 SV_TessFactor 语义的数组，内部因子用 SV_InsideTessFactor 语义。

这里埋下了整篇最反直觉的一段：并行不只是硬件的事实，也是编译器的一种决策。这个留到坑里细说。

【从0到1】

分五个里程碑。

第一个里程碑，把骨架搭起来。目标是让一个带曲面细分的 Shader 能编译通过。做法分三步。先新建一个包含文件存 Hull 和 Domain 的代码，加上包含保护。再把之前平面线框的 Shader 复制一份改名。最后给三个通道都加上 target 4.6，分别是 forward base、additive、deferred，并且在包含平面线框之后再加一句包含曲面细分的文件。验证方法很直接：材质挂上去，场景里放一个 Quad，能正常渲染出灰白线框就说明骨架通了。这一步还没切任何东西，属于播种阶段。

第二个里程碑，让 Hull 程序合法。目标是从一个空函数演进到能通过编译的完整声明。关键代码有两块。第一块是函数本体：输入是三个控制点的 Patch 加一个控制点编号，返回 Patch 里对应的那个元素。第二块是五个属性，必须一起写。domain 指定 tri，告诉它处理三角形。outputcontrolpoints 指定 3，一个 Patch 出三个控制点。outputtopology 指定 triangle_cw，新三角形按顺时针定义，和 Unity 其他三角形保持一致。partitioning 指定 integer，先用整数切分。patchconstantfunc 指向因子函数。验证方法是故意少写一个属性，看编译器报什么错，再补上。五个属性缺一不可，报错信息会明说配置不全。

第三个里程碑，写因子函数。目标是让三角形真的被切开。先定义因子结构：三个边因子加一个内部因子。函数一开始把四个值全设成 1，语义是不切。验证方法是把全部因子改成 2。这时候画面会变：每条边被分成两段，每个三角形在边上多出三个顶点，中心再多一个顶点，原来的一个三角形变成六个小三角形，Quad 是两个三角形，所以总数是 12。再改成 3，边被分三段，中心没有顶点，取而代之的是内部冒出一个内三角，外圈用三角形带连过去。规律是偶数因子有中心点，奇数因子有中心三角。因子继续加大，会出现多层嵌套，每往里一层，子边数减二，直到剩一或零。

第四个里程碑，让 Domain 程序生成顶点。目标是接住细分器给出的坐标，还原完整顶点数据。关键点在于细分器不生成顶点，它只给重心坐标 barycentric coordinates，三个分量分别是第一、第二、第三控制点的权重。Domain 程序对每个新顶点调用一次，通过 SV_DomainLocation 语义拿到这组权重。做法是先按权重把位置插出来，再写一个宏把同样的三路加权展开到法线、切线、三套 UV 上。唯一的例外是实例 ID：既然曲面细分和 Instancing 不能共存，这个字段就不复制。最后 Domain 程序不自己算插值器，而是把插值好的顶点数据交给原来的顶点程序，直接返回它的结果，着色逻辑一行都不用改。验证方法是把因子调回 1，画面应该和没开曲面细分时完全一致。

第五个里程碑，解决控制点的语义冲突。目标是把管线真正串起来，这也是三段接力里最后一段接插件。这一步会撞上一个报错：位置语义重复使用。原因是顶点阶段和 Hull 阶段都想用 POSITION 语义。解法是给控制点单独定义一个结构，位置的语义换成 INTERNALTESSPOS，其余字段照抄。这个结构叫 TessellationControlPoint，只在顶点阶段和 Hull 阶段之间流通。然后把顶点程序改成原样搬运，把 Hull 程序、因子函数、Domain 程序的参数类型统统换成这个新结构。验证方法是编译通过，Quad 正常显示，因子为 1 时没有视觉变化。

到这里骨架才算立住。之后才是这篇文章真正有意思的部分：因子怎么算。

先把因子做成一个可配置的统一值，范围 1 到 64，因为硬件对每个 Patch 的细分上限就是 64。再在材质面板里加一个折叠区块，只在属性存在时才画出来。

接着引入一个边因子函数。它接受一条边的两个控制点，返回这条边的因子，内部因子取三条边的平均值。这是因子部分唯一还需要口述的代码。

后面三种启发式我只说结论，代码略。第一种是世界空间边长：给一个理想边长属性，范围 0.1 到 1，因子等于实际边长除以理想边长，再用一个 shader_feature 关键字和统一模式切换。第二种是屏幕空间边长：把控制点转到裁剪空间做透视除法，乘以屏幕高度换算成像素，属性范围改成 5 到 100。第三种是视图距离：回到世界空间边长，再除以边中点到摄像机的距离，物体越远切得越少。

屏幕空间那一版有个细节值得记。裁剪空间范围是负一到一，两个单位才对应整个屏幕高度，所以算出来的边长被高估了一倍，等效于瞄准了一半的像素值。文章说这不重要，用屏幕高度的主要目的只是让细分依赖分辨率。换成视图距离那一版，视野变化就不影响细分，所以放大缩小的游戏不能用这种简化。

【踩坑与边界】

四个坑。

第一个坑，共享边的 Patch 必须算出同一个因子。症状是网格出现可见裂缝。根因是相邻两个 Patch 对同一条边给出不同因子，新生成的顶点在边上对不齐。修复思路是保证算法对称：所有边走同一套逻辑，区别只是控制点参数的顺序。浮点误差理论上会带来微小差异，但肉眼看不出来。

第二个坑，内部因子看起来是错的。症状是用 OpenGL Core 时，立方体每个面的两个三角形拿到截然不同的内部因子，而在 Quad 上不明显。根因不是逻辑错误，是编译器生成的代码有 bug：算内部因子时本该依次用三个边因子，实际三次都取了索引 2。修复办法看起来很荒唐，把边因子的计算在内部因子那里再显式抄一遍。逻辑上是重复计算，编译器理应优化掉，可这一抄就对了。原理是编译器会为了并行把因子函数拆成三个分支进程，拆开之后就再也优化不掉重复调用。文章最后给了更彻底的写法：先算三个顶点的世界位置，再让边因子和内部因子都调用同一个接受两个位置的版本，编译器反而选择不分叉，重复调用被消除。这个坑最值得记，它说明着色器代码的写法会影响编译器的并行决策，而不只是结果。

第三个坑，Domain 程序的位置语义。前面提过，必须换成 INTERNALTESSPOS，否则编译不过。被这个报错卡住的时候，很容易以为是结构体字段顺序错了。

第四个坑，整数因子的跳变。integer 模式下，因子就算设成小数，最终也是整数切分，级别之间切换很生硬。把 partitioning 改成 fractional_odd 之后过渡变平滑，多出来的那段边会分离、生长，或者缩小、合并。为什么优先用 odd 而不是 even？因为 odd 能处理因子 1，even 最低只能用 2。

边界和限制要交代清楚。阴影通道这次没开曲面细分，阴影仍按原网格计算。GPU Instancing 和曲面细分不共存。每个 Patch 的硬件细分上限是 64。Shader Target 最低 4.6。还有一点，因子是由每个 Patch 单独算出来的，所以它天然带有几何相关的抖动，物体一动，切分密度就会跟着变，这是特性不是缺陷。

【收束】

三句话。曲面细分是控制点、Hull、Domain 三段接力，不是一个函数。密度由四个因子决定，三条边加内部一个。因子怎么算决定了最终效果，边长和屏幕空间是两种最朴素的启发式。

什么时候该用：需要轮廓细节、需要近处加密的时候用它；细节能用法线贴图解决，或者要大量实例化渲染的时候别用。

不过，切开的三角形目前只是一堆更多的小平面，表面本身没有变复杂。下一集要把这些新顶点推离原表面，用置换贴图把平面变成真正的高低起伏，还要让阴影跟着一起变形。
