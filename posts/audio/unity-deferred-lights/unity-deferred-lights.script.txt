【钩子】
二〇一八年冬天，我照着教程写 Unity 内置管线的延迟光照。G-Buffer 已经填好，我把默认光照 shader 从 Graphics 设置里移除，换成自己的。第一版跑起来挺像回事：方向光有颜色，点光源有衰减，聚光灯也能照亮地面。接着三个问题冒出来。HDR 一关，天空盒整片变黑。切到聚光灯，屏幕黑得只剩一层灰。阴影走到远处，边缘像被刀切过。这三个问题都跟光照公式没关系。真正难的是另一件事：用尽量小的几何体圈住每盏灯的影响范围，再在屏幕空间把像素的世界坐标、材质、阴影和衰减重新拼起来。这就是本期的中心命题。听完这一期，能得到一条完整的手写延迟光照链路，从第二个 Pass 一直到点光源的立方体 cookie，也能知道哪些边界只有自己写 shader 才会碰到。

【用了什么】
延迟光照在 Unity 内置管线里的位置很明确。几何阶段先把材质写进 G-Buffer，也就是几何缓冲。所有不透明物体画完，光照阶段才开始。每盏灯一个独立的 Pass，修改的是屏幕图像，不是场景里的物体。
灯的形状由影响范围决定。方向光影响整个画面，所以画一个全屏 quad，也就是全屏四边形。聚光灯只影响一个圆锥，所以画一个金字塔。点光源影响一个球，所以画一个球体。这些几何体不负责显示颜色，它们只是光照 Pass 的载体。灯覆盖到哪里，光照就算到哪里。
它和延迟着色不是一回事。延迟着色把完整材质存下来，最后统一算一次光照。这里做的是延迟光照，光照 Pass 自己从 G-Buffer 取反照率、高光颜色、平滑度和法线，再自己算 BRDF，也就是双向反射分布函数。
G-Buffer 的纹理分工明确：反照率、高光颜色和平滑度、法线。光照 Pass 读它们，就像读一份已经摊开的材质清单。
HDR 和 LDR 是两条颜色路径。HDR 下光照直接相加。LDR 下光照要先做指数编码，所以多出第二个 Pass，专门负责解码。stencil buffer，也就是模板缓冲，不是可选项，它决定第二个 Pass 和聚光灯金字塔能画到哪些像素。
这一段先把位置摆清楚：延迟光照不是一套公式，而是一组按范围组织的屏幕空间 Pass。

【为什么用】
先说旧办法的痛点。前向渲染里，每盏灯都要在每个物体上重新算一遍。灯一多，draw call 上去，shader 里的光照分支也上去。一个像素可能被十几盏灯反复着色，最后只留下一个颜色。材质越复杂，这种重复越贵。
延迟光照把材质和光照拆开。几何阶段只写一次 G-Buffer。光照阶段不再关心场景里有多少物体，只关心灯覆盖了屏幕上的哪些像素。像素数大致等于灯的影响面积，而不是物体数乘灯数。灯增加时，成本更接近线性。复杂材质的光照代码也只写一份，所有物体共享。
代价同样明显。G-Buffer 是多张渲染目标，写入和读取都要带宽。半透明物体不适合写 G-Buffer。多重采样抗锯齿和延迟光照配合起来也麻烦。移动端对带宽更敏感，收益经常抵不过开销。光照 Pass 还要自己重建世界坐标、自己处理阴影，代码量并不小。
所以它有明确的适用边界。灯多、材质复杂、画面以不透明物体为主，延迟光照值得考虑。灯少、半透明多、低端移动设备、强依赖 MSAA，前向渲染更稳。这一篇只做学习实现，不追求性能优化。
回到中心命题：延迟光照省下的是重复着色，付出的是重建像素信息的复杂度。

【难在哪】
第一个难点是屏幕空间重建世界坐标。现象很直接：光照 Pass 里拿不到 G-Buffer 的 UV 坐标，Unity 不提供这个接口。原因在于光照 Pass 不是普通的物体渲染，它没有那套顶点 UV 语义。机制上只能自己从裁剪空间算。顶点阶段用 ComputeScreenPos 得到一个四维齐次坐标，片元阶段再除以它的 w 分量，才得到真正的屏幕 UV。这一步必须在片元里做，顶点里做出来的是插值后的近似。
世界坐标也不是现成的。要从相机原点穿过当前片元，打到远平面，得到一条射线，再用片元深度缩放射线。方向光时，全屏 quad 的四个顶点法线正好可以当作射线。聚光灯时，射线要从金字塔顶点位置自己构造。
机制可以拆成三步。射线先缩放到远平面，让它的 Z 分量归一，再乘远平面距离。然后按深度缩放射线，得到视图空间坐标。最后用相机到世界的矩阵转到世界空间。深度本身要从深度纹理采样，再线性化。线性化的意义是：射线对应的 Z 值，等于射线击中物体时的长度除以射线总长度。
第二个难点是 HDR 和 LDR 两条颜色路径。HDR 下光照直接相加，混合模式是一加一。LDR 下颜色先编码，第二个 Pass 再解码，混合模式变成目标色乘源色。写死任何一种，另一种模式都会出错。
第三个难点是阴影和衰减要手写。AutoLight 里的宏是为前向渲染准备的，不认延迟光照。阴影贴图变量不能随便声明，点光源和聚光灯的阴影变量已经在 UnityShadowLibrary 里定义过。cookie 光纹理、距离衰减、锥形衰减、平台通道宏，全都要自己接。阴影贴图还有最大距离，超过以后内置 shader 会渐隐，手写采样不会。
所以每个光照 Pass 最后都在做同一件事：把颜色、方向、阴影、cookie、距离这几个因子乘起来。
回到中心命题：难点不在公式，在重建和拼装。

【从0到1】
第一个里程碑，让第二个 Pass 只画非背景。目标是 HDR 关闭时天空不变黑。关键代码块是第二个 Pass 的模板配置。目的是给全屏解码 quad 加一道门槛，只让不属于背景的片元通过。输入是模板参考值和读掩码，二者都取 _StencilNonBackground。步骤是把参考值、读掩码设成这个标记，前后两面的比较都设成相等。验证方法是关掉 HDR 看天空盒，天空恢复，物体光照正常。这里有个容易误判的现象：直接复制第一个 Pass 会让除天空外全部变黑，因为模板值和背景标记不匹配。第二个 Pass 不是第一个 Pass 的复制品。模板缓冲从第一个 Pass 继承，但测试条件必须单独写。

第二个里程碑，解码 LDR 光照。目标是还原指数编码后的颜色。关键代码块只有一句，对光照缓冲采样后取负的以二为底对数。物理意义先讲清楚：LDR 要把超出范围的光照压进零点到一的区间，用的是指数映射；颜色等于二的负 C 次方，C 越大，编码值越暗。解码就是反过来取负对数。输入是 _LightBuffer 的采样结果，输出是线性的光照颜色。步骤是第二个 Pass 用全屏 quad 按屏幕 UV 逐像素解码。验证时对比 HDR 和 LDR 两条路径，亮部不能发灰，暗部不能丢细节。HDR 开启时不该走这段代码。全屏 quad 只负责把 _LightBuffer 搬回线性空间。

第三个里程碑，重建世界坐标并读 G-Buffer。目标是把屏幕上的每个像素还原成场景里的位置和材质。关键代码块是最后那次矩阵变换：视图空间位置乘上 unity_CameraToWorld，得到世界坐标。
输入有三样：屏幕 UV、深度纹理、顶点阶段送来的射线。输出是世界坐标，以及从 G-Buffer 读出的反照率、高光颜色、平滑度和法线。
步骤分四步。第一，顶点阶段用 ComputeScreenPos 得到齐次 UV。第二，片元阶段除以 w，采样 _CameraDepthTexture，再做线性化，得到零点到一的深度。第三，把射线缩放到远平面，再乘深度，得到视图空间位置。第四，用矩阵转到世界空间。
读 G-Buffer 时，反照率取第一张纹理的 RGB。高光颜色取第二张纹理的 RGB，平滑度取同一张纹理的 Alpha 通道。法线取第三张纹理的 RGB，乘二减一，从零点到一还原到负一到一。
验证方法很直接。把世界坐标可视化，它应该和场景几何完全对齐。把法线可视化，应该是一张彩色的球面图。这里有个笔误要避开：原文把相机 G buffer 纹理的变量名拼错了，知道是笔误就行。平滑度是标量，不是三维向量。
写到这里再回看中心命题：范围决定画多少，重建决定画得对不对。

第四个里程碑，算 BRDF 并配置方向光。目标是用 Unity 的标准光照函数算出最终颜色。关键代码块是 UNITY_BRDF_PBS 的调用。
输入包括反照率、高光颜色、一减反射率、平滑度、法线、视线方向、直接光和间接光。步骤是先用相机位置减世界位置，归一化得到视线方向；再用 SpecularStrength 从高光颜色里提出反射强度；间接光的两项都置零，因为延迟光照这里没有环境光贡献；直接光用光源颜色和光源方向填。输出是这一盏灯在这个像素上的颜色。
另一个关键代码块只有一句：把 _LightDir 取反后再赋给光的方向。目的是修正方向语义。Unity 给的 _LightDir 是光到表面，BRDF 要的是表面到光，不取反，明暗会整个反过来。验证方法是拿内置延迟 shader 做对照，高光位置和明暗过渡应该一致。
混合模式用一加一，把当前光照叠加到已有图像上，不能擦除前面的结果。变体用 multi_compile_lightpass，它会把所有光照配置展开；再补一个 UNITY_HDR_ON 的开关。其余配置和样板略。

第五个里程碑，把光照范围做成几何体，并处理阴影和衰减。目标有三个：方向光、聚光灯、点光源共用一份代码；阴影在远处平滑消失；每盏灯有正确的 cookie 和距离衰减。
先说范围。方向光用全屏 quad。聚光灯用金字塔，金字塔作为普通三维物体渲染，背面剔除，前面没有遮挡时才画。另一个 Pass 往模板缓冲里写标记，把光照限制在金字塔体积内。因此这个 Pass 要关掉剔除和深度测试，混合模式改成可配置的两项。点光源换成球体，其余逻辑相同。聚光灯离相机太近时，相机会进入体积，或者近平面把体积切开，模板缓冲就失效。这时要改画金字塔的背面，而且只在必要时这么做，因为它会多画很多片元。
再说射线统一。关键代码块是用 lerp 在两种射线来源之间插值，判断依据是 _LightAsQuad。
方向光时这个值为一，直接用顶点法线当射线。聚光灯和点光源时这个值为零，要把顶点位置用 UnityObjectToViewPos 转到视图空间，再把 X 和 Y 取反。这里用插值而不是条件分支，是因为插值对 GPU 更友好。验证方法是方向光和聚光灯都打开，世界坐标都能对齐，聚光灯不再整片发黑。
阴影部分。关键代码块是 UnityComputeShadowFadeDistance 和 UnityComputeShadowFade 这一对函数。目的是替代内置 shader 在阴影贴图边缘的硬截断。输入是世界坐标和视图深度，也就是视图空间位置的 Z 分量。步骤是先算渐隐距离：Stable Fit 以阴影贴图中心为球心算距离，Close Fit 用视野深度；再算零点到一的渐隐因子；最后把它加到阴影衰减上，并限制在零点到一。验证时把相机拉远，阴影应该在最大距离之前柔和消失，而不是突然断掉。
方向光阴影采样用 _ShadowMapTexture，但声明要放在 SHADOWS_SCREEN 关键字里，否则会跟 UnityShadowLibrary 里的定义冲突。聚光灯阴影换用 SHADOWS_DEPTH 关键字，采样函数换成 UnitySampleShadowmap，传入世界坐标乘世界到阴影矩阵的结果，软硬阴影的细节由函数内部处理。点光源阴影是立方体贴图，参数改成光到表面的反向向量。这些是同一套结构的不同分支，配置略。
最后看距离衰减。关键代码块是查找纹理采样。输入是光向量、_LightPos 第四个分量里的光照范围、以及 _LightTextureB0。步骤是光向量点乘自己得到距离平方，乘范围做缩放，当成 UV 去采样，再用 _UNITY_ATTEN_CHANNEL 取当前平台对应的通道。验证时看灯光边缘，应该平滑变暗。
聚光灯的 cookie 还有两个细节。矩阵变换出来的是四维齐次坐标，X 和 Y 要除以 W。而且前后会出现两个光锥，只有负 W 的前向锥有效，另一个要乘零裁掉。cookie 采样时加一个负八的 mip 偏移，可以压掉相邻片元坐标差异带来的硬边。点光源的 cookie 是立方体贴图，把世界坐标转到光照空间后直接按方向采样。

【踩坑与边界】
第一个坑，HDR 关闭后天空全黑。症状是天空盒消失，物体正常。根因是第二个 Pass 的模板测试没有排除背景，解码 quad 把天空也写成了黑色。修复是在第二个 Pass 里把模板参考值和读掩码都设成非背景标记，比较函数设成相等。
第二个坑，复制第一个 Pass 后，除天空外全黑。症状和上一个相反，看起来像模板全被拒绝。根因是第一个 Pass 的模板配置继承过来，但第二个 Pass 的测试条件没有跟着改。修复是保留模板继承，把测试条件单独写。
第三个坑，方向光算出来明暗颠倒。症状是高光跑到背面，亮面变暗面。根因是 _LightDir 的语义。Unity 提供的是光到表面的方向，BRDF 需要表面到光的方向。修复是在赋给光源结构时取反。
第四个坑，聚光灯整片黑。症状是金字塔范围内几乎没有光。根因有两个：一是金字塔顶点的射线没有转到视图空间，二是转过去以后 X 和 Y 方向反了。修复是用 UnityObjectToViewPos 把顶点位置转到视图空间，再乘一个 X、Y 为负一、Z 为一的向量，最后用 _LightAsQuad 插值，和方向光的法线射线统一。
第五个坑，阴影边缘硬切。症状是阴影在最大距离附近突然消失，边缘像锯齿。根因是手写采样只采阴影贴图，没有内置 shader 的渐隐逻辑。修复是用 UnityComputeShadowFadeDistance 算距离，用 UnityComputeShadowFade 算零点到一的因子，加到衰减上。Stable Fit 和 Close Fit 的算法不同，函数已经把两种模式封装好了。
第六个坑，cookie 边缘有硬边。症状是聚光灯照到斜面上的 cookie 图案边缘发锯齿。根因是相邻片元的 cookie 坐标差异大，GPU 选到的 mip 级别对当前表面太低。修复是用带偏置的纹理采样，把 mip 偏移设成负八。
边界也要说清楚。LDR 的混合模式写死会破坏 HDR，正确做法是把源混合和目标混合做成材质属性，按模式切换。距离衰减纹理的通道在不同平台不同，必须用 _UNITY_ATTEN_CHANNEL。软阴影模式用单独的关键字区分。阴影跳过看起来很美，但 UNITY_BRANCH 本身也有成本，只有软阴影这种多次采样的场景才值得，方向光阴影只有一次采样，跳过反而亏。这套实现属于 Unity 内置管线，依赖 Built-In shader settings、Stencil 和这些内置 cginc，搬到可编程渲染管线不能照抄。
这些坑逐个看，仍然是范围和重建两件事。

【收束】
三句话收尾。第一，延迟光照把材质写一次，光照按灯的影响范围在屏幕空间算。第二，每个 Pass 的关键是重建世界坐标，再读 G-Buffer、算 BRDF、乘上阴影和衰减。第三，HDR 与 LDR、方向光与聚光灯与点光源、cookie 与阴影，差异都落在关键字、混合模式和几次坐标缩放上。
什么时候该用：灯多、材质复杂、不透明物体为主，延迟光照有优势。什么时候不该用：半透明多、移动端、强依赖 MSAA，前向渲染更稳。
下一期可以继续往优化走：怎么按光源类型裁剪变体，怎么减少阴影采样，或者把这套代码接回内置管线的完整光照流程。
